# Relecture de code : moteur de détection et persistance d'une appli Android anti-arnaque

Vous êtes un ingénieur Kotlin/Android senior. Répondez en français. On vous soumet le cœur d'une appli
qui interrompt l'utilisateur (« écran STOP ») quand une action sensible (SMS de code, demande de
validation bancaire, appli de prise en main à distance…) survient pendant un appel téléphonique ou dans
les 15 minutes qui suivent. Une erreur dans un sens laisse passer l'escroc ; dans l'autre, elle
interrompt sans raison.

## Architecture (pour lire le code)

- Module `:domain` (Kotlin pur, aucune dépendance) : modèles, `DetectionEngine` (fonction pure
  `(état, signal, réglages) → (état, journal, décisions)`), `CallWindow`, ports, `ProcessSignalUseCase`.
- Module `:app` : `RoomDetectorStore` (état + journal dans une transaction Room, un signal à la fois sous
  `Mutex`, repli sur l'état en mémoire si le stockage échoue), `DetectorMapping` (lignes ↔ domaine),
  `SettingsRepository` (DataStore).
- Les capteurs Android qui produiront les `Signal` ne sont PAS encore écrits, ni l'exécuteur des décisions.

## Ne PAS signaler (choix délibérés ou limites déjà documentées)

- Le moteur ne lit aucune horloge : l'heure vient du signal. Un appel « en cours » depuis plus de 8 h est
  traité comme une fin d'appel manquée.
- Pas de SQLCipher ; targetSdk 36 ; aucun capteur ni exécuteur écrit.
- Limites connues, déjà écrites : (1) un processus redémarré APRÈS une panne de stockage ne connaît pas
  l'appel en cours ; (2) un nouvel appel arrivé pendant un appel dont la fin a été manquée hérite de
  l'ancien ; (3) protection rallumée en plein appel : pas de réveil pour le rappel d'appel long ; (4)
  journal jamais élagué ; (5) une annulation de coroutine entre la validation et l'affichage laisse le
  STOP enregistré (borné par la retenue de 60 s).
- Style, nommage, commentaires, formatage, suggestions d'architecture générales.

## Ce qui est demandé (au plus 10 constats)

Des défauts RÉELS de logique ou d'intégrité : un STOP qui devrait s'afficher et ne s'affiche pas (ou
l'inverse), un état ou un journal incohérent, une exception qui coupe la protection, un problème de
transaction Room ou de concurrence, une annulation avalée, un cas limite de date (bornes, ordre des
signaux), une ligne mal relue. Pour chaque constat : fichier et fonction, **scénario d'échec concret**
(séquence de signaux avec leurs heures, ou état stocké → résultat faux), gravité (CRITIQUE / ÉLEVÉE /
MOYENNE / FAIBLE), certitude (CERTAIN / PROBABLE / À VÉRIFIER), correctif proposé en quelques lignes.

« Aucun défaut trouvé sur ce point » est une réponse attendue et utile. N'inventez aucune API : si vous
doutez du comportement d'une API (Room `withTransaction`, DataStore), écrivez À VÉRIFIER.
